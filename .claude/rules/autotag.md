# Analyse automatique des tags

Cadre : [0029](../../docs/decisions/0029-analyse-automatique-des-tags-sur-l-appareil.md), [0030](../../docs/decisions/0030-tags-de-l-ia-en-couche-separee-et-masquables.md), [0031](../../docs/decisions/0031-tags-de-l-ia-en-suggestions-avec-score.md). Code : `lib/core/autotag/`.

- Ce que trouve l'IA est une **suggestion**, pas un tag : elle vit dans `sound_auto_tags` (avec son `score`, 0 à 1), **jamais dans `sound_tags`** (ceux de l'utilisateur) — ne rien écrire de l'IA dans `sound_tags` ni de l'utilisateur dans `sound_auto_tags`. Une suggestion est **toujours affichée** (pas de masquage) et n'entre dans les tags que quand l'utilisateur l'ajoute depuis le formulaire. Recherche, listes et sélecteur ne lisent **que** `sound_tags` : ne pas y remettre d'union avec `sound_auto_tags`. Le score est une confiance relative (softmax des écarts réduits, `MoodTagRule.suggestions`), pas une probabilité calibrée : ne pas le présenter comme telle ([0031](../../docs/decisions/0031-tags-de-l-ia-en-suggestions-avec-score.md))
- L'analyse ne touche **jamais** un son traité ni un son qui n'est pas de type musique, et ne marque **jamais** un son traité : passer en « traité » fige les suggestions. L'éligibilité se revérifie au moment d'enregistrer les suggestions (`LocalAutoTagDataSource.applyDecisions`), pas seulement au moment de l'analyse. Une ligne existante n'est jamais modifiée par l'analyse
- La synchro fusionne `sound_auto_tags` par union, dernière écriture gagnante (`updated_at`), sans jamais supprimer (`_mergeSoundAutoTags`) : ne pas la remettre en « remplace tout le dossier » comme `sound_tags`. Le snapshot publie encore `hidden = 0` pour les appareils en v45, et ignore (en le journalisant) une table sans `score`
- Elle ne s'orchestre que depuis `AutoSyncCoordinator` (après le pull et après l'insertion de sons, jamais dans un écran) et s'arrête en Mode Spectacle, en arrière-plan ou pendant une passe de synchro. Ne rien ajouter qui s'exécute sur le chemin d'un déclenchement de pad
- La fiche d'un son (`SoundEditForm`) montre l'état d'analyse du son (`SoundAnalysisStatus`, via `AutoTagAnalysis`) et propose « Analyser » tant qu'elle n'a pas commencé : le bouton ne lance rien lui-même, il passe par `AutoSyncCoordinator.requestAutoTag(firstSoundId:)`, donc par les mêmes refus (Mode Spectacle, arrière-plan, synchro, passage déjà en cours), dont la raison est affichée. Le son demandé passe en tête de file, mais le passage continue sur les autres sons éligibles
- Inférence : **uniquement** via `OnnxSession`/`MuqAnalyzer` (isolate de travail). L'API Dart de `flutter_onnxruntime` gèle le thread de l'interface pendant l'inférence (≈ 410 ms/clip mesurés) — le paquet ne sert qu'à embarquer la bibliothèque native
- Décodage : uniquement via `decodeAnalysisClips` (symbole natif appelé directement, tampons libérés, file ADR 0001 tenue ≈ 100 ms par clip). `test/core/autotag/pcm_decoder_test.dart` échoue si le comportement détourné de flutter_soloud change : ne pas l'ignorer, ne pas élargir le décodeur sans lui ajouter un cas
- Une suggestion doit viser un tag déjà existant (catalogue EMOTION_STYLE) : l'analyse ne crée aucun tag. `kMoods` suit l'ordre des lignes de `assets/autotag/text_latents.f32`
- Les statistiques de recentrage portent sur **toutes** les empreintes (`sounds.auto_embedding`), pas seulement les sons éligibles ; `auto_tagged_at` signifie « décision prise (suggestions enregistrées ou non) »
- Le pack (`AutoTagPackRelease`) porte en dur adresse, taille et SHA-256 : changer de modèle = nouveau pack publié + nouvelle version de l'app. Un fichier au nom final dans le dossier du pack est toujours complet (`.part` puis renommage)
- Journaliser via `AppLog` (une ligne par événement : démarrage, bilan, raison d'arrêt) et `AudioLoadLog.trace` pour le détail par fichier. Licence : modèles CC BY-NC → usage non commercial, attribution affichée dans Paramètres
